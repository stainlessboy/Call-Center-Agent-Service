# Evals — проверка агента числом

Зачем: смена промпта, модели или middleware до сих пор проверялась вручную —
задать десяток вопросов и посмотреть глазами. Так не видно, что улучшив один
сценарий, сломали три других. Здесь набор эталонных вопросов и набор
проверок, которые дают одно число на каждый прогон и позволяют сравнивать
версии между собой (пункт П.7б в [AGENT_ROADMAP.md](AGENT_ROADMAP.md)).

## Что где лежит

| Файл | Что делает |
|------|------------|
| `evals/dataset.py` | Эталонные случаи (`GOLDEN_CASES`) — вопрос, язык, стартовый `dialog`, ожидаемый инструмент |
| `evals/runner.py` | Гоняет случай через **настоящий** граф агента и возвращает структурный результат |
| `evals/stubs.py` | Оффлайн-заглушки модели и БД, чтобы прогон работал без ключей |
| `evals/evaluators.py` | Чистые функции-оценщики, каждая возвращает вердикт 0..1 |
| `scripts/eval_agent.py` | CLI: прогон набора, отчёты, сравнение с базой |
| `docs/evals/` | Отчёты (`.json` — машинный, `.md` — для чтения) |
| `.github/workflows/evals.yml` | Оффлайн-самопроверка на каждый PR, живой прогон по запросу |

## Как запускать

```bash
# Оффлайн: без ключей, без БД, без сети. Проверяет, что связка жива.
python3 scripts/eval_agent.py

# Только часть набора — быстрее при отладке
python3 scripts/eval_agent.py --limit 10
python3 scripts/eval_agent.py --filter mortgage

# Живой прогон: настоящая модель и настоящая БД. Это и есть измерение.
python3 scripts/eval_agent.py --live

# С выгрузкой эксперимента в LangSmith (нужен LANGSMITH_API_KEY)
python3 scripts/eval_agent.py --live --langsmith

# Сравнение с предыдущим отчётом: падает, если tool_match просел больше 2 п.п.
python3 scripts/eval_agent.py --live --baseline docs/evals/2026-09-04.json
```

Оффлайн-режим — не измерение качества модели. Он проверяет **проводку**:
что случаи прогоняются, инструменты вызываются, оценщики считают. Качество
измеряется только `--live`.

## Оценщики

| Ключ | Что проверяет | Когда 0 |
|------|---------------|---------|
| `tool_match` | Вызван ли ожидаемый инструмент | Вызван другой, или инструмент вызван там, где ждали ответ без него |
| `category_match` | Совпала ли категория продукта | Показали автокредит вместо ипотеки |
| `reached_db` | Дошёл ли ответ до реальных данных | Общая отписка вместо названий продуктов или текста FAQ |
| `no_pii_leak` | Нет ли в ответе PII | Номер карты, ПИНФЛ, паспорт в ответе; либо бот повторил телефон клиента |
| `language_match` | Отвечает ли бот на языке вопроса | На узбекский вопрос ответ по-русски |
| `latency_under` | Уложился ли ход в бюджет | Дольше порога (по умолчанию 8 с) |
| `no_error` | Не упал ли ход | Исключение внутри графа |

Важная деталь: вердикт может быть **неприменим** (`applicable: false`) — тогда
он не входит в проценты. Иначе неприменимые случаи молча набивали бы метрику
бесплатными единицами и порог перестал бы что-либо ловить.

Ещё одна: `expected_tool: None` — это утверждение, а не пропуск. Оно значит
«на приветствие инструмент вызывать не нужно», и вызов инструмента там
считается ошибкой.

## Как читать отчёт

`docs/evals/<дата>.md` — сводка по каждому оценщику (сколько применимо,
сколько прошло, процент) и список провалившихся случаев с комментарием. JSON
рядом — то же самое машинно, он и подаётся в `--baseline`.

## Порог регрессии

`--baseline <файл>` сравнивает текущий `tool_match` с прошлым и завершается
ненулевым кодом, если просадка больше 2 процентных пунктов (меняется флагом
`--max-drop`). Порог не нулевой намеренно: один случай из полусотни — это
2 п.п. шума, а не регрессия, и нулевой порог сделал бы гейт неработающим от
постоянных ложных срабатываний.

## Как добавить случай

В `evals/dataset.py`, в `GOLDEN_CASES`:

```python
_case(
    id="mortgage_uz_list",
    text="qanday ipoteka bor?",
    lang="uz",
    expected_tool="get_products",
    expected_category="mortgage",
    must_reach_db=True,
    notes="Каталожный вопрос на узбекском — не должен уходить в FAQ",
),
```

`expected_tool` принимает и список, если вопрос честно допускает две
маршрутизации. После добавления прогоните `pytest tests/test_evals.py`:
`validate_dataset` проверит уникальность id, известный язык и что имя
инструмента вообще существует — опечатка в имени иначе сделала бы случай
непроваливаемым.

## CI

- **На каждый PR** — оффлайн-джоб: тесты оценщиков плюс прогон 10 случаев.
  Без секретов, ловит поломку самой связки.
- **Живой прогон** — только по метке `run-evals` на PR или ручным запуском
  (`workflow_dispatch`). Он платный: один вызов модели на случай.
